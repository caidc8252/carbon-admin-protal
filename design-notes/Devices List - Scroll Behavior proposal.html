Devices 列表 — 滚动交互方案

你的诉求：数据多时的竖向滚动放到外层滚动条（参考 Customers），列多时的横向滚动收在列表内部。 而现状是横竖两个方向都在外层滚动。下面是分析、迫使我们必须取舍的那一条 CSS 限制，以及三个可以实际滚动体验的实时方案。 目前产品代码尚未做任何改动 —— 你选定方向后我再动手实现。

核心取舍

下面三件事，最多只能同时满足两件 —— 纯 CSS 做不到三全

这一点项目规范里已经写明（ui-spec/ui-spec.md §3.3）。要把横向滚动收在表格内部，外层容器必须加 overflow-x —— 而该容器随即成为 sticky 表头的定位上下文。于是表头只能吸顶到这个容器内部，无法再吸顶到整页。

CSS 限制

相互冲突的三件事

诉求 #1
竖向滚动放在外层
由整页唯一的 .content 滚动条上下滚动行 —— 搜索栏一起滚走，完全和 Customers 一致。
诉求 #2
横向滚动收在列表内
多出来的列在卡片内部横向滚动；标题栏、搜索栏和整页都不会跟着左右平移。
诉求 #3
竖向滚动时表头吸顶
长列表往下滚时，列标题（thead）和计数行始终吸顶停留在顶部。
好消息：你明确提出的两条诉求 —— #1（外层竖向）+ #2（内层横向）—— 是可以同时成立的， 也就是方案 B。唯一要放弃的是 #3（往下滚时表头保持吸顶）。 如果你更看重吸顶表头，方案 C 能同时保住 #2 + #3，但代价是竖向滚动改到列表内部（放弃 #1）。

基线 — 横竖两个方向都在外层整页滚动 现状

Devices 现在的做法。宽表格溢出 .content，于是整页左右滑动 —— 标题栏和搜索行都跟着漂走。竖向滚动时表头能正常吸顶。

B

把横向滚动收在卡片内 你要的方案

竖向仍在外层整页（同 Customers）；横向被锁在列表卡片内。标题栏和搜索行永远不会左右移动。代价：往下滚时列表头不再吸顶 —— 会跟着行一起滚走。（这就是 ListCard 上现有、但 Devices 尚未启用的 scrollX 模式。）

竖向： 外层 ✓ 横向： 列表内 ✓ 表头吸顶： 否 — 会滚走 ✗
模拟 .content 视口在卡片内往 → 滚 · 整页往 ↓ 滚（表头会离顶）
方案 C · 规范明列的例外项
C

有界数据网格 — 横竖滚动都在内部，表头吸顶 §3.3 例外

表格区变成一个固定高度、双向滚动的网格。表头吸顶到该网格的顶部，标识列（SN）可以冻结在左侧便于对照。代价：竖向滚动条变成列表自己的内层滚动条 —— 不再是最外层整页的那根，因此与 Customers 的模式不一致。

竖向： 内层（非外层）⚠ 横向： 列表内 ✓ 表头吸顶： 是（+ 冻结 SN）✓
模拟 .content 视口内层网格可往 ↓ 和 → 滚 · SN 列冻结

还有个方案 0 —— 规范明确的首选：根本不上横向滚动。Devices 已有 Columns 菜单；文本用省略号 + tooltip 截断，让用户自行收起列来适配宽度。横向滚动是这一招不够时的兑底。

我的选择
方案 B，叠在方案 0 之上 —— 这正是你要的。

先保留规范的默认行为：默认 8 列时表格是能装下的，Columns 菜单 + 省略号（方案 0）意味着大多数用户根本不会触发横向滚动条。一旦有人加足够多的可选列导致溢出，再启用卡片现有的 scrollX 包裹层（方案 B），让溢出部分在卡片内滚动，而不是拖着整页左右滑。竖向滚动保持与 Customers 完全一致。

B 的真实代价是竖向滚动时的吸顶表头。但对 Devices 来说这个损失很轻微 —— 行是分页的（默认 25/页），列表很少长到表头会滑出屏外。如果后面发现吸顶表头比外层竖向滚动条更重要，那就是改用方案 C的信号。

  • 改动最小、最安全：方案 B 是 ListCard 已内置的一个 prop（scrollX），CSS 也现成 —— 无需新组件。
  • 可逆：可以加个门控 —— 只有当列真的溢出时卡片才横向滚动，默认宽度下保持干净观感。

选一个，我来实现

  1. 方案 B — 把横向滚动收在卡片内，接受竖向滚动时表头不再吸顶。（我的推荐，符合你的诉求）
  2. 方案 C — 有界数据网格：保留吸顶表头 + 冻结 SN，接受竖向滚动移到列表内部。
  3. 仅方案 0 — 不加横向滚动，靠 Columns 菜单 + 截断来适配。最简单，滚动行为不变。
  4. B + 门控 — 采用 B，但只在列溢出时才启用内层横向滚动（默认宽度下保持干净）。
