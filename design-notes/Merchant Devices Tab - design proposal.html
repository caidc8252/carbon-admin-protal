Design proposal · v2 · Devices tab redesign · review before build

Customer detail · Devices tab (MERCHANT customers)

Per the corrected model: DEVICE_APPLICATION (per-device installed/requested/diff apps) + DEVICE_EVENT (per-device telemetry) become the new source of truth. Merchants no longer hold an app-level aggregation — apps are deployed by ISO operators on a per-terminal basis in the customer portal, and the admin platform only observes.

What's changing on the customer detail tab strip
  • Tab Stores & terminals → renamed to Devices. The store strip stays (multi-store filtering remains useful), but the heading and content now emphasize terminals + their app deployment status, not stores.
  • Tab Apps → removed entirely. There is no merchant-level app aggregation anymore — admin observes app state device-by-device via the new tab.
  • Kept — terminal SN remains clickable; opens device detail with Back returning to customerDetail/devices.
  • Added — every device row expands to show its INSTALLED_APPS, computed DIFF_APPS, and recent DEVICE_EVENT stream — all read-only.

A
KPI strip rewritten for the new model
All 4 tiles are device-shaped (no app-level rollups). "Devices with diff" rolls up the DIFF_APPS computed metric across the fleet; "Install failures · 7d" reads DEVICE_EVENT for EVENT_TYPE = 应用安装失败 in the trailing 7-day window.
B
Apps column shows installed / requested
Compact device-level rollup: 3 / 3 means 3 apps requested, 3 installed at the correct version. Color tells the story — green / amber / red.
C
Deployment column tells the operator what
A single chip + one-liner. "1 pending · Smart Receipt 1.1.7 → 1.1.8" is enough for triage; full detail lives in the expanded body.
D
Diff card surfaces above Installed/Requested
Order matters — for any device with diff, the first thing admin sees on expand is "what's wrong". Installed + Requested live below as supporting context. The diff card hides itself when the device has no diff.
E
Behavior flags as small mono chips
KIOSK / BOOT / LOCKED / HIDDEN / DISABLED. From IS_KIOSK_MODE, IS_AUTO_START_ON_BOOT, IS_UNINSTALLABLE = false, IS_LAUNCHER_ICON_HIDDEN, IS_APP_LAUNCH_DISABLED. Tooltips spell out the field on hover.
F
Events stream is filtered + truncated
Default = last 24 h, capped at ~6 most recent. "View full event log" routes into a dedicated device events screen (or the device-detail page's Events tab). Time stamp + dot color + 1-line description — Linear-style.

2How DIFF is computed (data flow)

Per the spec: walk REQUEST_APPS.PKG_NAME; look up each in INSTALLED_APPS.PKG_NAME. If not found, or request.versionCode > installed.versionCode, it lands in DIFF.

REQUEST_APPS (ISO config)

com.northwind.pos.pro 4.3.2 (1432)
com.northwind.smartreceipt 1.1.8 (118)
com.helios.loyaltyplus 1.3.4 (134)

INSTALLED_APPS (device reported)

com.northwind.pos.pro 4.3.2 (1432)
com.northwind.smartreceipt 1.1.7 (117)
com.helios.loyaltyplus 1.3.4 (134)

DIFF_APPS (derived)

com.northwind.smartreceipt 1.1.8 ← 1.1.7
Other pkgs match → DIFF empty for them.
Two cases that land in DIFF:
  1. Missing install — REQUEST pkg has no matching INSTALLED row → device hasn't downloaded it yet.
  2. Stale version — INSTALLED exists but versionCode is lower than REQUEST → device has it but needs an upgrade.
We do not surface "apps installed by the user that the ISO didn't request" — those are outside the deployment contract and aren't actionable from admin.
G
DIFF is computed client-side from the JSONB
No separate DIFF_APPS column is needed in the table API — we compute it from request_apps + installed_apps at render time. (Server can still cache it for KPI queries.)
H
VERSION_CODE wins over VERSION_NAME
Comparison uses the integer VERSION_CODE, never string-compares VERSION_NAME (e.g. "1.10" > "1.9" only works numerically).

3Strategy display (per-app, per-device)

Per the new model, strategy is stored inside each REQUEST_APPS row — no longer a separate table. Three urgency variants drive the chip color; the rest is one inline string.

CASUAL · default
CASUAL · Wi-Fi/Ethernet only · 02:00–04:00 window
Quiet upgrade when the device is idle — won't interrupt the merchant.
IMMEDIATE · urgent
IMMEDIATE · Any network
Force-upgrade as soon as the device next reports in. Reserved for security patches.
CUSTOM · manual
CUSTOM · Wi-Fi/Ethernet + Cellular (cap 200 MB) · Next boot or 10m idle · 22:00–01:00 window
All knobs set by the ISO. We render every field in order.
I
No modal for strategy
It all fits in one line. Adding a modal for the new model felt like ceremony — the previous design used one because we had bulk vs per-terminal duality to explain. That goes away.
J
INSTALL_WINDOWS = pill-line
Each window renders as HH:MM–HH:MM. If multiple windows are configured, they comma-separate. Spec says "不允许跨24点" so we don't have to deal with cross-midnight ranges.

?Decisions still on you

  1. Store strip — keep at the top of Devices tab (filters the device list, as in mock)? Alternative: drop, and add a Store column to the table — fewer chrome elements but slightly less obvious.
  2. Empty-state placement — when a customer has 0 terminals (just signed contract): big illustration-free empty card ("No terminals registered yet"), or hide the tab entirely until first device sync?
  3. "View full event log" — should this route into the existing device-detail page (with an Events tab), or open a dedicated full-screen events table filtered by this device? I'd vote former (less new surface, returns to where admin came from).
  4. DIFF computation level — compute at render time client-side (proposed), or expect the backend to provide a precomputed DIFF_APPS on DEVICE_APPLICATION? The spec already lists it as a JSONB field; my proposal still leans on it for queries (KPI tile) but ignores it in the row UI in favor of fresh derivation. Tell me if backend-provided is canonical.
  5. Behavior flags — the 5 booleans are surfaced as inline chips. Is that the right priority, or should they live under an "info" affordance (hover popover) to keep the row cleaner?
  6. Mock data work — once you approve, I'll seed SEED_DEVICE_APPLICATIONS + SEED_DEVICE_EVENTS over the bridged legacy terminals (replacing the old SEED_MERCHANT_APPLICATIONS / SEED_DEVICE_INSTALLED_APPS / SEED_DEVICE_APP_STRATEGIES). The four App Pool tables (APPLICATIONS / APPLICATION_VERSIONS / PARTNER_APPLICATION / PARTNER_APPLICATION_VERSION) stay — they describe the publisher/ISO catalog, not the merchant deployment.
